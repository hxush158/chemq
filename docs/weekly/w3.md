# W3 · 取知识：RAG 的每一环怎么坏

**能力目标**：RAG 出了问题，你能判断是 chunking、embedding、检索还是生成这一环坏的。

**达标线**：`citation_acc ≥ 0.90`，Recall@5 ≥ 0.85，无命中时必须拒答。

---

## 概念卡

**① chunking**
把长文档切成检索单元。本项目按标题层级切，400–800 token，重叠 ~80。
⚠️ 切太碎丢上下文（"该系数"指的哪个系数？），切太大稀释相关性。
**制度类文档按条款切**比按固定长度切好得多 —— 条款本身就是语义单元。

**② embedding**
把文本映射成向量，语义近的向量近。
⚠️ 中文和专业术语是重灾区。"综合能耗"和"单位能耗"在向量空间里很近，但口径完全不同。
这正是为什么**不能只靠向量**。

**③ 向量检索 vs BM25**
向量管语义，BM25 管精确词。
⚠️ 本项目的典型失败：问"折标煤系数依据哪个标准"，答案里的关键 token 是 `GB/T 2589`。
向量会把它压成"某个标准编号"的模糊表示，和 `GB/T 50034` 分不开；BM25 一击即中。
反过来"能耗怎么算"没有共同词，只有向量能救。

**④ RRF (Reciprocal Rank Fusion)**
`score = Σ 1/(k + rank)`，把多路召回的名次融合。
→ 项目里：`solutions/rag_w3.py` 的 `HYBRID_SQL`
⚠️ k 是"名次的钝化程度"：k 太小 = 头部一路说了算（等于没融合），
k 太大 = 名次信息被抹平（退化成"出现在两路里就行"）。60 是原论文经验值，值得自己扫一遍。

**⑤ citations**
回答里的每个说法能指回原文。Claude 的 search results content block 可以自动产出引用。
⚠️ **有引用 ≠ 引用对**。要单独测"引用的那段话真的支持这个说法吗"。

**⑥ 检索到了也要拒答**
两种情况：最高分低于阈值（召回都是弱相关）；top-1 和 top-2 指向**互相矛盾的口径版本**。
⚠️ 第二种在数据治理项目里极其常见（老版制度和新版制度都在库里）。
正确行为是**把矛盾报出来让人裁决**，不是挑一个说得更顺的。

## 破坏实验 · 关掉一路召回

**做什么**

1. 建一个 8 道题的知识小评测集，其中 3 道答案含精确标识符（`GB/T 2589`、`P02`、条款号）
2. 分别跑：只向量 / 只 BM25 / hybrid
3. 再做一次：把 chunk 从 600 token 改成 100 token，重跑 hybrid

**预期观察**

| | 含精确标识符的题 | 意图模糊的题 |
|---|---|---|
| 只向量 | 大幅失败 | 好 |
| 只 BM25 | 好 | 大幅失败 |
| hybrid | 好 | 好 |
| hybrid + 100token chunk | 召回得到，但**答案缺上下文**（"该系数"不知道指谁） |

**说明了什么**

RAG 有四个独立的失败面，症状完全不同：
召回不到（检索问题）、召回到但不全（chunking 问题）、召回到但答错（生成问题）、
召回到矛盾的（数据治理问题）。只看最终答案对不对，你分不清是哪一个。
**所以每一环都要能单独测。**
