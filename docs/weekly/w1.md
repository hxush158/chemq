# W1 · 看懂一次 API 调用

**能力目标**：拿到任意一次 Claude 调用，你能说清它花了多少钱、钱花在哪、怎么降。

**达标线**：`make eval WEEK=1` 的 `intent_acc ≥ 0.90`，且能拿出 `cache_read_tokens > 0` 的证据。

---

## 概念卡

> 用法：先盖住"背面"，看术语能不能自己说出定义 + 项目里对应哪行代码。

**① token / context window**
一次请求的计费和限制单位。中文一个字通常 ≈ 1–2 token，比英文贵。
→ 项目里：`Usage.input_tokens` / `output_tokens`（`llm.py`）
⚠️ 常见误解：context window 大 = 可以随便塞。**塞进去的每个 token 每次都要付钱**，而且太长会稀释注意力。

**② system vs user**
system 是"你是谁、规则是什么"，user 是"这次要干嘛"。
→ 项目里：`Llm.cached_system(...)` vs `messages=[{"role":"user",...}]`
⚠️ few-shot 放哪边决定了缓存能不能命中 —— 这是本周破坏实验的主题。

**③ structured outputs**
用 JSON Schema 约束输出，保证拿到合法结构。参数是 `output_config.format`，
Python SDK 用 `
(output_format=<pydantic model>)` 直接拿对象。
→ 项目里：`Llm.parse()` + `schemas.QueryPlan`
⚠️ 不是"让模型输出 JSON"那么简单 —— 它是**约束解码**，模型物理上生成不出违反 schema 的 token。
所以你不再需要 try/except json.loads 和重试。

**④ prompt caching**
把稳定的长前缀缓存起来，命中时输入按约 10% 计费，写缓存按 125%。
`cache_control: {"type":"ephemeral"}` 打在前缀最后一块上，**缓存的是从头到这一块的整个前缀**。
默认 TTL 5 分钟，可选 1 小时（贵一倍）。
→ 项目里：`Llm.cached_system()` 把 cache_control 打在最后一块

⚠️ **最小可缓存长度按模型不同，差 8 倍**：

| 模型 | 下限 |
|---|---|
| Opus 5 / Fable 5.1 | 512 |
| Sonnet 5 | 1,024 |
| **Haiku 4.5** | **4,096** |

短于下限时 `cache_control` 被**静默忽略**——不报错、不建缓存、`cache_read` 永远 0。
本项目 router 的前缀约 1,200 tokens：在 Sonnet 上能缓存，在 Haiku 上不能。
**这是「便宜模型」的隐藏成本**：单价低，但你可能用不上缓存。

⚠️ 前缀必须逐字节稳定。前面任何一个字符变了，缓存全部失效。顺序：稳定的在前，变化的在后。

⚠️ 判断缓存有没有生效，看 `cache_creation_input_tokens` 和 `cache_read_input_tokens`
**两个数**。都是 0 = 压根没建缓存（多半是长度不够）；write>0 但 read 一直 0 = 前缀不稳定。
只看 `cache_read` 分不清这两种。

**⑤ 模型分级路由**
用便宜模型做分类/路由，贵模型做生成。
→ 项目里：`model_router` (Haiku) vs `model_sql` (Sonnet)
⚠️ 不要一上来就全用最贵的然后想着"以后优化"。分级是架构决定，不是优化项 ——
它逼你想清楚"哪一步真的需要强推理"。

**⑥ usage 记账**
每次调用返回 `usage`，含 input/output/cache_read/cache_creation 四个数。
→ 项目里：`Usage.cost_usd`
⚠️ cache_creation 是按 **125%** 计费的（写缓存要钱）。所以只调用一两次的场景，
开缓存反而更贵。缓存在"同一前缀反复调用"时才划算。

**⑦ thinking / effort**
让模型先想再答，或调节思考的投入程度。
→ 项目里：`Llm.complete(thinking_budget=...)`
⚠️ 思考 token 也计费，且算 output。分类任务开 thinking 基本是浪费。

## 破坏实验 · 缓存在什么条件下才存在

先量，再改，别靠猜。`count_tokens` 接口不计费。

### 实验 A：同一份 prompt，换个模型

```bash
cd ai
uv run chemq tokens "8月产量多少"     # 先看前缀多长、各模型的下限是多少
```

然后：

```bash
# 1. 默认 Haiku 4.5，连跑三次
uv run chemq plan "8月产量多少"

# 2. 换 Sonnet 5，再连跑三次
CHEMQ_MODEL_ROUTER=claude-sonnet-5 uv run chemq plan "8月产量多少"
```

**预期观察**

| | cache_write | cache_read | 说明 |
|---|---|---|---|
| Haiku 4.5 | 0 | 0 | 前缀 ~1,200 < 下限 4,096，缓存**没建** |
| Sonnet 5 第 1 次 | >0 | 0 | 建缓存，这次付 125% |
| Sonnet 5 第 2、3 次 | 0 | >0 | 命中，输入按 10% 计费 |

**说明了什么**

「用便宜模型省钱」不是无条件成立的。Haiku 单价是 Sonnet 的一半，但在这个前缀长度上
它拿不到缓存折扣；Sonnet 单价贵一倍，命中缓存后重复输入只付 10%。
**算总账要把缓存算进去**，而不是只看每百万 token 的标价。

⚠️ 两次之间别隔超过 5 分钟——默认 TTL 到了缓存就没了，你会误以为是别的原因。

### 实验 B：把前缀弄不稳定

用 Sonnet（因为 Haiku 上根本看不到变化）：

1. 正常跑 3 次，记下 `cache_read`
2. 把 `router.py` 里的 `FEW_SHOT` 从 `cached_system(...)` 挪进 `user` 消息，再跑 3 次
3. 挪回 system，但在**最前面**加一句 `f"当前时间 {datetime.now()}"`，再跑 3 次

**预期观察**

| | cache_read |
|---|---|
| 正常 | 第 2 次起 >0 |
| few-shot 挪到 user | 仍 >0，但缓存的内容变少了 |
| 前缀加了时间戳 | **一直 0** |

**说明了什么**

第 3 种最危险：代码看起来毫无问题，"加个时间戳方便调试"是很自然的动作，
但它让缓存彻底失效，而功能上完全看不出来——线上成本翻几倍，只能靠账单发现。

**引申**：还有什么常见写法会无声地破坏前缀稳定性？
（提示：dict 序列化顺序、`set` 的迭代顺序、把检索结果放在 system 开头）
