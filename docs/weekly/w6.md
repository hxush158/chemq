# W6 · 说清楚它好不好

> ⚠ 已被阶段二计划替代（[`../10-flagship-plan.md`](../10-flagship-plan.md)），保留作参考，不再按本文执行。

**能力目标**：能用数据说明这个系统好在哪、什么时候不能信它。这是企业敢不敢上线的分界线。

**达标线**：60 题全量评测跑通，CI 门禁生效，产出《可行性与选型报告》。

---

## 概念卡

**① eval set 设计**
分层：简单/中等/困难 × 取数/知识/混合/**该拒答**。
⚠️ 最容易漏的是**该拒答**那一类。只测"能答对多少"，会得到一个"什么都敢答"的系统。

**② 执行准确率 vs 精确匹配**
比结果集，不比 SQL 字符串。
→ 项目里：`run_eval.rows_match()` 无序比对、0.5% 容差
⚠️ 比 SQL 文本会把大量正确答案判错（写法不同而已）。

**③ LLM-as-judge**
用模型给开放式回答打分。
⚠️ judge 有偏好（更长的、更自信的得分高）。**必须用人工标注的子集校准 judge 本身**。
judge 不校准就等于换了个更贵的随机数。

**④ 回归测试与 CI 门禁**
每次改 prompt 都要跑，防止"修好一个坏三个"。
→ 项目里：`.github/workflows/eval.yml`，`refuse_acc < 1.0` 直接不让合并
⚠️ 真实评测花钱，所以 PR 只跑自检 + 单测，main 分支才跑全量。

**⑤ 成本看板**
按问题类型、按模型、按天统计 token 和金额。
→ 项目里：`qa_audit` 表的 `cost_usd` / `input_tokens` / `cache_read_tokens`
⚠️ 要能回答"如果 100 个人每天问 20 次，一个月多少钱" —— 这是甲方一定会问的。

**⑥ 适用边界**
写清楚**什么场景不能用**。
⚠️ 这才是报告里最值钱的一页。一份只说好话的报告，业务方不敢签字。

---

## 必做

1. 评测集从 20 题扩到 **60 题**，补齐四个象限，特别是"该拒答"那一类
2. 实现 LLM-as-judge 给混合型回答打分，并用 10 条人工标注校准它
3. CI 跑通，门禁生效
4. 成本看板：SQL 查 `qa_audit` 出一张按周的成本/延迟/准确率表
5. 写《智能问数可行性与选型报告》：
   - 准确率分层结果（哪类问题能用、哪类不能）
   - 成本模型（按用户数和问题量推算）
   - 失败模式清单（口径漂移、扇出、检索失败、拒答不足）
   - **明确的不适用场景**
   - 上线前提条件（语义层先建、口径先定、人工复核流程）

## 破坏实验 · 让评测指标骗你

**做什么**

1. 往评测集里塞 5 条**标注错误**的题（标准答案是错的）
2. 跑评测，看总分怎么变
3. 再做一次：把 20 道简单题复制成 60 道，难题保持 5 道，看总分
4. 最后：只用 LLM-as-judge 不用执行准确率，跑一遍，对比两个指标的排序

**预期观察**

- 错标注会让一个正确的系统"看起来变差"，而你会去改本来没问题的代码
- 题目分布一倾斜，总分立刻虚高 —— **平均分掩盖了难题上的失败**
- LLM-as-judge 和执行准确率给出的排序可能不一致

**说明了什么**

**评测本身也需要被评测。** 一个漂亮的分数可能来自：题目太简单、标注有错、
指标选错、judge 有偏好。报告里必须说清楚评测集怎么建的、覆盖了什么、**没覆盖什么**。

**引申**：如果甲方问"你这 92% 是怎么来的，我能信吗"，你怎么答？
