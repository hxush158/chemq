## W3 第 1 步 · 评测数据链路：标准答案从哪来、凭什么可信（11/14）

**Hui 的讲法**

> 标准答案随着时间变化和源数据变化不是一个固定值，而是根据一个计算方法得到，所以用 SQL 算；
> cases 里有和常见场景相关的问题意图和 method，通过 nz-power 审口径是为了保证问的数和 nz-power 的口径一致。
> holdout 独立计算是为了避免数据处理过程中产生错误。

**纠正**

1. 时间本身不会让答案变：题目写的是具体日期，基准日固定为 2026-09-30。会变的是数据（上游重算或修正，
   比如 W2 的 avg_price 43 行、字典升到 11.2）。用 SQL 还有一个更重要的原因：口径写成 SQL 才能被审查、
   被复现，也才能拿到 Snowflake 上复核；手填的数字没人能审。
2. cases 在 chemq 仓库（`domains/nz_power/eval/cases.yaml`），nz-power 只负责审。审口径防的是一种评测自己发现不了的错：
   参考 SQL 和系统按同一种理解算，理解错了两边照样一致，评测照样打勾。
3. holdout 那句是对的。更准确地说：holdout 的答案由 nz-power 从原始文件独立算，不经过 MART，也不经过我们的参考 SQL，
   所以服务库或 MART 本身有错、参考 SQL 写错，都能被它发现。

**修订版**

> 标准答案不是手填的数字，而是 SQL 算出来的：数据被上游修正时重算一次就行，口径写成 SQL 也才能审、能在 Snowflake 上复核。
> 但参考 SQL 和系统可能犯同一个理解错误，这时评测照样通过，所以要加两道外部检查：
> nz-power 审每道题的口径（method），保证"问的数该不该这么算"；
> holdout 的答案由 nz-power 从原始文件独立计算，不经过我们的服务库和 SQL，用来发现数据处理链路本身的错误。

## W3 第 2 步 · 调规则修在哪一层（11/15）

**Hui 的讲法**

> 调规则时要修在最通用的那一层，是要分析处理规则的执行逻辑；给每道错题加专门的示例，是没办法穷尽可能出现的错误。

**补充**（没有事实错误，补两点）

1. "最通用的那一层"就是错误根源所在的那一层：口径没写清楚就改字典，规则缺了就改规则，代码走错就改代码。修一次，同一类题都受益，包括没见过的 holdout 和真实用户的问题。
2. 给错题加专门示例还有一个更隐蔽的害处：golden 分数会虚高。示例等于把答案透露给了模型，golden 测的就变成了"见没见过"，而不是"会不会"，最后在 holdout 上露馅。这和 W2 few-shot 泄题是同一个机制。

**修订版**

> 失败要找到根源所在的那一层去修：字典、规则还是代码。修一次，同类问题都对，包括没见过的题。
> 给每道错题加专门示例，一是穷尽不了，二是等于把答案透露给模型，golden 分数虚高，holdout 上才露馅。
