# RAG 设计说明（W3）

> 这个文件之前被 `domains/chem/data/01_schema.sql` 和 `rag.py` 引用了两次，但一直没写。

## 1. Embedding 选型：Amazon Bedrock Titan Text Embeddings V2

| | 结论 |
|---|---|
| 模型 | `amazon.titan-embed-text-v2:0`，输出 1024 维，和 `kb_chunk.embedding vector(1024)` 一致 |
| 地区 | `ap-southeast-2`（Sydney），新流程下 project 按联系地址自动分到这里 |
| 输入上限 | 8,192 token / 50,000 字符，chunk 400–800 token 远低于上限 |
| 中文 | 支持，但官方说明是"针对英文优化" —— **所以 BM25 这一路对中文更重要** |
| 凭证 | `aws login --profile chemq`：浏览器登录，临时凭证每 15 分钟自动轮换，不存长期 key |

为什么选它而不是 Voyage / bge-m3：和 W5 上云、求职需要的 AWS 经验最契合。
备选（以后可以做 A/B）：

- **bge-m3**（本地，MIT，1024 维）：中文最好；国内化工企业数据不出内网时最可能的生产方案
- **Voyage voyage-4**：Anthropic 推荐的 embedding 服务商，2 亿 token 免费额度

换模型只要维度仍是 1024，schema 不用动；维度不同就要改 `vector(N)` 并重建索引。

## 2. 中文切词：字二元组（bigram）

PostgreSQL 的 `to_tsvector('simple', ...)` 按空格和标点切词，中文没有空格，
一整句会变成一个词项 —— BM25 对中文等于没开。

做法（`chemq/textseg.py`）：

- 中文按字二元组切：`综合能耗` → `综合` `合能` `能耗`
- ASCII 标识符整体保留并拆出各部分：`GB/T 2589-2020` → `gb/t` `gb` `2589-2020` `2589` `2020`
- 写入：`tsv = array_to_tsvector(%(lexemes)s::text[])` —— 按原样当词项，不再经过解析器
- 查询：`%(tsq)s::tsquery`，词项之间用 OR —— 问句里的「到底」「怎么」文档里没有，AND 会全部落空

已知代价：bigram 有跨词边界的噪声（「合能」），`ts_rank` 没有 IDF，不是真正的 BM25。
语料只有几份文档时可以接受，由向量那一路互补。

## 3. 检索 SQL

两路**各自先 `ORDER BY ... LIMIT N`**，再用 RRF 融合：`score = Σ 1/(k + rank)`。

- 只有 `ORDER BY embedding <=> x LIMIT n` 这个形状才会用上 HNSW 索引
- 向量这一路同时带出原始余弦相似度，供"无命中"判断用

参数在 `config.py`：`rag_rrf_k=60`、`rag_candidates=20`、`rag_top_k=5`。

## 4. 无命中判断：不能看 RRF 分数

RRF 分数是名次，不是相关度。向量检索永远返回最近的 N 条，第一名永远是 1/(k+1)。

`rag.is_no_hit()` 看两个信号，任一成立就算找到了：

1. 向量那一路最高余弦相似度 ≥ `rag_min_cosine`
2. 问题里的 ASCII 标识符（GB/T、P02）在某条结果正文里字面出现

只靠 BM25 撞上几个中文二元组（「成本」「怎么」）不算。

⚠ `rag_min_cosine = 0.35` 是**占位值**，第 5 步用评测集标定：
把「该命中」和「不该命中」的问题各跑一遍，看两组余弦分布在哪里分开。

## 5. 权限

检索走只读账号 `chemq_ro`，需要 `GRANT SELECT ON kb_document, kb_chunk TO chemq_ro`
（在 `domains/chem/data/03_semantic_views.sql`）。写入（ingest）走 `chemq_app`。

## 6. 知识文档与检索评测集

知识文档在 `domains/chem/kb/docs/*.md`，文件开头的 front matter 对应 `kb_document` 的字段：

| doc_id | 文档 | 类型 | 切块方式 |
|---|---|---|---|
| KB-ENE-2026 | 能耗考核管理办法（2026 版） | 制度 | 按条款（`###`） |
| KB-OPS-STOP | 生产装置停车分类与统计规定 | 制度 | 按条款（`###`） |
| KB-MET-2026 | 经营指标口径说明 | 口径字典 | 按指标（`##`） |
| KB-RPT-202603 | 2026 年 3 月经营分析月报 | 月度经营分析 | 按章节（`##`） |

条款本身就是语义单元，很多只有一两百 token，比 400–800 的建议值小 —— 对制度类文档这是对的，
不要为了凑长度把两个条款拼在一起。每个 chunk 写入时要在正文前加上「《文档标题》› 章 › 条」，
否则单独看"检修期间合格产量为零……"这一段，模型不知道说的是哪份制度。

检索评测集 `domains/chem/eval/kb_golden.jsonl`，每题标注应该命中的 `(doc_id, section)`：

- `identifier`（4 题）：含 GB/T 2589、0.1229、P05、P02 —— 测 BM25 那一路
- `fuzzy`（8 题）：和原文几乎没有共同词，如"氨厂开工不足" —— 测向量那一路
- `refuse_with_source`（1 题）："利润怎么算" —— 库里有依据，依据就是"不支持"
- `no_hit`（3 题）：库里没有 —— 测 `is_no_hit()`，也用来标定 `rag_min_cosine`

Recall@5 只在前三类上算；`no_hit` 单独统计误答率。

## 7. 入库（ingest）

```
make install-rag          # 数据库 + boto3[crt]（>=1.41 才读得了 aws login 的凭证）
aws login --profile chemq # 临时凭证，最长 12 小时
make ingest-dry           # 只切块看结果
make ingest               # 切块 -> Titan 向量化 -> 写库
```

两条设计：

- **先全部向量化，再一次事务写库。** 向量化是几十次网络调用，中途凭证过期或断网，
  库里不会出现"一半新一半旧"。
- **`domains/chem/kb/docs` 是唯一来源。** 每次整体同步：先删后插，文件夹里没有的文档也从库里删掉，
  重跑结果一样。所以 `chemq_app` 对两张 kb 表多给了 DELETE（业务表不给）。

`make seed` 会重建 schema、清空知识库，seed 之后要重跑 `make ingest`。

首次入库：4 篇 34 块，3981 tokens，约 6 秒。

## 8. 检索评测（只评"找没找对"）

```
make eval-rag      # 需先 make ingest；问题向量缓存在 runs/kb_query_emb.json，重跑不调 AWS
```

同一批题、同一段 SQL，三种方式各查一次：只用向量 / 只用 BM25 / 混合。
关掉某一路的办法是把那一路的 `LIMIT` 设成 0（`hybrid_search(..., mode=...)`），
所以比较的只是"用不用这一路"，没有别的变量。

- **Hit@1**：第 1 条就是正确章节。知识库只有 34 块，前 5 条已占全库 15%，Hit@5 几乎总是满分，
  真正能分出高低的是这个。
- **Hit@5**：前 5 条里至少有一条是正确章节。生成答案只需要一条对的依据。
- **Recall@5**：标注的几个正确章节，前 5 条找到了几个。
- 无答案题不计分，只记"全库最相似那一块"的余弦，和有答案题的放在一起看有没有空隙 —— 第 5 步用。

检索里没有大模型，同样的输入结果每次一样，跑一次就够（W2 的 SQL 评测要连跑 3 次看噪声）。

跑之前的预期：标识符题 BM25 好、向量差；模糊问法反过来；混合不比两者中较好的那个差。

**基线结果（2026-10，34 块 / 13 题）**

| | 向量 | BM25 | 混合 |
|---|---|---|---|
| Hit@1 | 0.77 | 0.77 | **1.00** |
| Hit@5 | 0.92 | 1.00 | 1.00 |
| Recall@5 | 0.85 | 0.81 | 0.91 |

- 两路各有 3 题没排第 1，而且**不重叠**：向量输在字面信息多的题（K03、K04、K13），
  BM25 输在问法模糊的题（K05、K06、K09）。合起来 13 题全部第 1 —— 这就是混合检索的价值。
- 预期"标识符题向量找不到"没成立：题里除了标识符还有"折标煤系数""停车"这类中文词，向量靠它们也找得到。
- 小代价：K05、K09 向量能找全 3 个正确章节，混合只找到 2 个 —— BM25 挤进来的结果把排在后面的推出了前 5。
- K13"利润怎么算"向量完全找不到（最高相似度 0.221），只靠 BM25 字面命中"利润"。
  它和无答案题最高值 0.192 只差 0.029，现行阈值 0.35 会把它判成无命中 —— 第 5 步要解决。

## 9. 无命中判断的标定

`rag.hit_signals()` 三个信号，任一成立就算"找到了"：

| 信号 | 条件 | 管什么题 |
|---|---|---|
| 余弦 | 向量这一路最高余弦 ≥ `rag_min_cosine` | 大多数题 |
| 标识符 | 问题里的 GB/T、P02 在结果正文里字面出现 | 向量最弱的题 |
| 术语 | 问题里的术语（`domains/chem/glossary.txt`）在结果正文里字面出现 | K13「利润怎么算」这类：语义不像，字面就是它 |

中文只认术语表里的词，「怎么」「安全」「审批」这种到处撞得上的不算 ——
否则"帮我写辞职信"也会被判成找到了。

**阈值 0.35 → 0.30**：K13 交给术语信号后，有答案题最低余弦 0.408，无答案题最高 0.192，取中间。
`make eval-rag` 会扫 0.15–0.45 各阈值下的误拒 / 误答，换模型或知识库大变后据此重新标定。

**分工**：

- 检索层只负责挡**完全无关**的问题（`no_hit`，误答必须为 0，否则退出码 1）。
- **擦边题**（`near_miss`，如"4 月单耗为什么升高"——库里只有 3 月月报）检索层分不清，
  因为它们和库里内容确实很像。只记录、不计分，第 6 步由大模型对照原文说"资料里没有"。

**旧测试改了一条**：原来认定"人工成本怎么算"应判无命中。但口径字典明确写了
"成本、利润、人工成本目前没有数据源"——正确行为是引用这条说"暂不支持"，旧预期是错的。

## 10. 带引用的回答（kb_answer.py）

```
问题 → Titan 向量化 → 混合检索前 5 条 → 无命中判断（第 5 步）
   ├─ 判"无"：直接回答"没找到"，不调 Claude，零成本
   └─ 判"有"：5 条作为 search_result 块交给 Claude（Sonnet 5）→ 回答 + 引用
```

- 每条检索结果是一个 `search_result` 块：`source` = `kb://文档ID#块ID`，`title` = 「《标题》› 章 › 条」，
  正文按段落拆成多个 text 块。Claude 按**整块**引用，拆细了引用才精确到段落。
- **引用和 structured outputs 不能同时开（400）**。所以这里不能像 W2 那样给一个 `refuse_reason` 字段，
  改用约定：资料相关但没回答问题时，回答以「【资料未覆盖】」开头，代码检测它判拒答。
- 三个拒答出口：`no_hit`（检索层挡住）/ `not_covered`（Claude 说资料没覆盖）/
  `no_citation`（答了但没有一条引用 —— 很可能凭记忆答，拦截）。
- 混合题：先跑 SQL，查询结果作为**普通文本**（不是 search_result，不能被引用）一起交给 Claude，
  规则写明数字只许照抄。知识库答不上时不算整体拒答 —— 数字还在，只是少了解释，记进 caveats。
- 系统提示里"资料未覆盖"的举例故意写得很泛：擦边题的具体内容出现在提示里就是泄题（W2 的教训），
  `test_system_prompt_does_not_leak_near_miss_questions` 盯着这一点。

评测：`make eval-kb`（一次）/ `make runs-kb N=3`（看噪声）。直接调 `answer_from_kb()`，不经过 router。

| 类别 | 指标 | 目标 |
|---|---|---|
| 有答案 13 | 引用正确率（没拒答，且引用里至少一条是标注章节） | ≥ 0.90 |
| 有答案 13 | 误拒 | ≤ 1 |
| 无答案 3 | 拒答（检索层挡住，不调 Claude） | 3/3 |
| 擦边题 4 | 拒答（`【资料未覆盖】`） | ≥ 3/4 |

## 11. 检索条数 5 → 8

K04「P02 那次停车之后的维修登记成什么类型？」要两条依据才能答：
月报"四、需要关注的事项"（2 月 9 日是**非计划**停车）+ 停车规定第四条（非计划停车的维修登记为"抢修"）。
前 5 条里只有第四条；模型看到的反而是"P02 本月连续运行"，于是以【资料未覆盖】拒答 ——
按它拿到的资料，这是对的，没有乱编。问题在检索，也在标注：第 4 步只标了第四条，评测显示"排第 1"是假象。

修正：K04 补标月报那一节；检索条数做对比实验（各跑 3 次，结果三次一致）：

| | 5 条 | 8 条 |
|---|---|---|
| 检索 Recall（混合） | 0.87 | **1.00** |
| 检索 Hit@1 | 1.00 | 1.00 |
| 引用正确率 | 0.92 | **1.00** |
| 误拒 | 1（K04） | **0** |
| 无答案题拒答 | 3/3 | 3/3 |
| 擦边题拒答 | 4/4 | 4/4 |
| 成本 / 20 题 | $0.124 | $0.151（+21%） |

改为 8 条。**更正第 8 节的一句话**：当时写"生成只需要一条对的依据，Hit@5 最重要"——
对单跳题成立，对 K04 这种多跳题不成立。Hit@1 两边一样，这次的提升全在 Recall 上。
