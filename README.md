# ChemQ

**Natural-language analytics over process-industry operations data — built as a 6-week curriculum in AI application engineering.**

A "ask your data" system for a chemical plant: someone types *"which sales region had the worst cash collection last month?"* and gets a number they can defend in a management meeting. The hard part is not generating SQL. It is making the answer **trustworthy** — correct metric definitions, no invented numbers, enforced data permissions, and a measurable accuracy figure you can put in front of a client.

## What this repository demonstrates

**A semantic layer, not raw-table access.** Metric definitions live in SQL views (`db/03_semantic_views.sql`) and a machine-readable dictionary (`kb/metric_dictionary.yaml`). The model may query the views and nothing else. "Output" means *qualified output excluding rework*; unit energy consumption is `Σ(consumption × coal-equivalent coefficient) / qualified output` with the coefficient read from a dimension table, never hard-coded. In enterprise Text-to-SQL, wrong *definitions* cost more than wrong *syntax* — and they are much harder to notice.

**Defense in depth against LLM-generated SQL.** Three independent layers, each covering the one above it:

| Layer | Blocks | Implementation |
|---|---|---|
| Intent classification | Out-of-scope questions, prompt injection | `router.py` + structured outputs |
| SQL guard | Writes, unlisted relations, missing `LIMIT`, catalog probing | `sqlguard.py` — **sqlglot AST parsing, not regex** |
| Database | Everything the first two miss | read-only role + row-level security |

Verified: the read-only account reads the semantic views fine, and is refused on `fact_*` detail tables and on any write — `permission denied`.

**Evaluation-first development.** The golden set's expected answers are **generated by executing reference SQL against the database** (`evals/build_golden.py`), so changing the data regenerates the answers instead of silently invalidating them. `compare.py` diffs two runs and reports not just the score delta but **which cases flipped** — a flat total can hide "fixed three, broke three". CI gates on refusal accuracy at 100%: a system that answers everything is worse than one that says "I don't have that".

**Cost engineering treated as architecture.** Per-call accounting of input / cache-write / cache-read / output tokens; per-model prompt-cache minimums encoded in the code; a labelled A/B harness for model and effort comparisons. Measured result on this workload: the "cheaper" model was **5× more expensive**, because its 4,096-token cache minimum made caching impossible at this prompt length.

## The data

Synthetic, 12 months, generated from `naming.yaml` with a fixed seed. Plant and product names are placeholders. Four phenomena are deliberately planted so the system can be tested against findings a human would recognise:

| Planted | Detectable as |
|---|---|
| Two-week turnaround on the ammonia plant, March 2026 | Monthly uptime 51.6%; unit energy consumption 130 → 134.8 kgce/t |
| Cash-collection anomaly, one region, August 2026 | 36.3% vs ~90% everywhere else |
| Methanol price decline from June 2026 | Volume and revenue diverge |
| Three unplanned shutdowns | All attributable to one plant |

Unit energy consumption *rises* during the outage because fixed energy load continues while output stops — the kind of domain behaviour that makes a synthetic dataset worth testing against.

## Architecture

Two answering engines run side by side and share one tool layer, one semantic layer and one safety layer. `make eval ENGINE=pipeline|agent` runs the same questions through either.

```
                              question
              ┌──────────────────┴──────────────────┐
              ▼                                     ▼
  Pipeline (pipeline.py)                  Agent analyst (agents.py)
  Router (Haiku, structured outputs)      Agent SDK (Sonnet)
   ├─ out of scope ─► refuse              tools=[]: no built-in tools at all
   ├─ metric    → text2sql (Sonnet)       3 in-process tools only
   ├─ knowledge → kb_answer               PreToolUse hook: audit + deny
   └─ mixed     → SQL first, then         turn and budget caps
                  kb_answer with rows     code Critic checks every number
              └──────────────────┬──────────────────┘
                                 ▼
        Shared tools (tools.py): list_metrics · run_semantic_query · search_knowledge
              │                                         │
              ▼                                         ▼
  sqlguard (AST · allowlist · v_* only · LIMIT)   hybrid retrieval (Titan + BM25 + RRF)
  read-only role + statement_timeout              no-hit check → cited answer or refusal
  semantic views v_* (metric definitions)

  External agents (Claude Code CLI, …) → mcp_server.py (stdio) → the same tools.py
```

There is no separate Narrator step. A metric question returns the SQL rows as the answer. A mixed question's prose comes from `kb_answer`, which is told to copy numbers from the rows. The agent writes its own answer, and a code Critic (`critic.py`, not a second model call) checks every number against the rows and cited text.

Three principles run through it:

1. **SQL computes the numbers; the model never does arithmetic.** Ratios and sums go in SQL. Where a model does write numbers, a code check compares them with the data.
2. **The semantic layer owns metric definitions.** Enforced by database grants and the sqlguard allowlist, not by prompt wording. Conventions live in shared places (metric dictionary, generated catalog, tool descriptions) so every engine gets them.
3. **Every layer assumes the one above it has a bug.** Each constraint only works in the layer it lives in. A prompt rule is a request; a tool list or a database grant is a constraint.

See [docs/01-architecture.md](docs/01-architecture.md) for the defence table, known gaps and the evaluation setup.

## Running it

Requires Docker Desktop and [uv](https://docs.astral.sh/uv/). macOS: `bash scripts/bootstrap-macos.sh` installs everything.

```bash
cp .env.example .env          # add CHEMQ_ANTHROPIC_API_KEY
make up                       # PostgreSQL + pgvector; first run builds schema and loads data
make doctor                   # environment check, including a live API call
make install-db
make test                     # SQL guard unit tests
make eval WEEK=1
```

`make eval` fails until `pipeline.answer()` is implemented — that is week one.

## Why a curriculum

Building this as a course rather than a product forced every decision to be *explained*, not merely made. Each week carries a "break-it lab" — deliberately break the system and observe how it fails, because failure modes teach mechanism in a way working code does not. Deliberately breaking prompt caching, for instance, showed that a debugging timestamp in a system prompt silently triples cost with no visible symptom.

The corrections are in the repository history and in `docs/journal/`, including the ones where my own initial design was wrong.
